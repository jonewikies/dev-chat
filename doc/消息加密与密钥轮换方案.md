# DevChat 消息加密与密钥轮换方案

本文档描述当前仓库已经支持的消息加密方式、密钥轮换边界和推荐操作步骤。

## 1. 当前实现

- 消息内容由后端在写入 `messages` 表前进行加密
- 当前算法为 `AES-256-GCM`
- 每条消息独立生成随机 IV
- 数据库存储字段包括：
  - `content`：密文
  - `content_iv`：随机向量
  - `content_tag`：认证标签
  - `content_key_version`：密钥版本号
- 仓储层读取消息时自动解密，因此前端和大多数业务服务仍消费明文内容

## 2. 当前边界

- 运行时当前只支持一个激活中的消息密钥
- 现阶段没有实现“按 key version 自动选择历史密钥解密”的多密钥运行时机制
- 因此密钥轮换不能采用热切换方式，必须采用离线全量重加密方式

这意味着：

- 不能直接修改线上 `ENCRYPTION_KEY` 后立即重启服务
- 必须先停止服务，完成历史消息重加密，再切换运行时密钥配置

## 3. 相关环境变量

后端运行时：

```bash
ENCRYPTION_KEY=当前生效的消息加密密钥
ENCRYPTION_KEY_VERSION=当前运行时写新消息时使用的密钥版本号
```

轮换脚本执行时额外使用：

```bash
OLD_ENCRYPTION_KEY=旧密钥
NEW_ENCRYPTION_KEY=新密钥
NEW_ENCRYPTION_KEY_VERSION=新密钥版本号
```

建议：

- 密钥使用 `openssl rand -hex 32` 生成
- 不要把密钥直接写进命令历史或共享文档
- 生产环境优先通过受控环境变量注入，而不是硬编码到脚本文件

## 4. 两类操作

### 4.1 历史明文补加密

适用场景：

- 数据库来自旧版本，部分消息还是明文
- 想离线确认当前库里是否还有未加密消息

命令：

```bash
cd server-web
npm run build
npm run migrate-message-encryption
npm run migrate-message-encryption -- --apply
```

说明：

- 第一次是预演，不写库
- 第二次加 `--apply` 后才落库
- 脚本会自动备份数据库

### 4.2 密钥轮换重加密

适用场景：

- 怀疑现有消息密钥泄露
- 按安全策略周期性轮换生产密钥
- 需要把历史消息统一升级到新的密钥版本

命令入口：

```bash
cd server-web
npm run build
OLD_ENCRYPTION_KEY=旧密钥 \
NEW_ENCRYPTION_KEY=新密钥 \
NEW_ENCRYPTION_KEY_VERSION=2 \
npm run rotate-message-encryption-key

OLD_ENCRYPTION_KEY=旧密钥 \
NEW_ENCRYPTION_KEY=新密钥 \
NEW_ENCRYPTION_KEY_VERSION=2 \
npm run rotate-message-encryption-key -- --apply
```

说明：

- 第一次是预演，只统计和抽样展示待处理消息
- 第二次加 `--apply` 后才真正重写数据库内容
- 脚本会自动备份数据库
- 脚本会在 `app_migrations` 里记录一次轮换执行结果

## 5. 推荐轮换 SOP

### 5.1 执行前准备

1. 确认当前服务可停止维护窗口
2. 备份数据库文件和 `.env`
3. 生成新密钥，例如：

```bash
openssl rand -hex 32
```

4. 规划新的 `ENCRYPTION_KEY_VERSION`，例如从 `1` 升到 `2`

### 5.2 正式步骤

1. 停止后端服务，确保轮换期间没有新消息写入
2. 执行预演：

```bash
cd server-web
npm run build
OLD_ENCRYPTION_KEY=旧密钥 NEW_ENCRYPTION_KEY=新密钥 NEW_ENCRYPTION_KEY_VERSION=2 npm run rotate-message-encryption-key
```

3. 检查输出里的 `targetRows` 是否符合预期
4. 执行正式重加密：

```bash
OLD_ENCRYPTION_KEY=旧密钥 NEW_ENCRYPTION_KEY=新密钥 NEW_ENCRYPTION_KEY_VERSION=2 npm run rotate-message-encryption-key -- --apply
```

5. 更新 `server-web/.env`：

```bash
ENCRYPTION_KEY=新密钥
ENCRYPTION_KEY_VERSION=2
```

6. 启动后端服务
7. 用真实账号发送一条消息并验证聊天、AI 总结、消息搜索是否正常

## 6. 验证清单

- 服务启动无解密错误
- 历史聊天能正常打开
- 新消息发送成功
- AI 总结仍能读取历史消息
- 关键词搜索仍可返回预期消息
- 数据库中的 `messages.content_key_version` 已切换到新版本

## 7. 风险与回滚

主要风险：

- 使用了错误的旧密钥，导致脚本无法正确解密历史消息
- 服务未停机时执行轮换，导致轮换窗口内出现新旧密钥混写
- 新密钥已写入环境，但数据库还未完成重加密，导致启动后无法解密旧消息

回滚原则：

- 轮换脚本在正式写库前会自动做数据库备份
- 如轮换失败，应先恢复数据库备份
- 恢复后把 `.env` 中的 `ENCRYPTION_KEY` 和 `ENCRYPTION_KEY_VERSION` 切回旧值
- 确认服务恢复正常后，再重新安排下一次轮换

## 8. 后续可选增强

如果后续希望把停机时间进一步缩短，可以继续演进为：

- 运行时支持“按 `content_key_version` 选择历史密钥解密”
- 新写入统一使用最新密钥，旧消息异步分批重加密
- 引入更完整的密钥管理系统，而不是只依赖 `.env`

在当前代码基础上，上述能力还未实现，因此不建议按热轮换思路执行。
